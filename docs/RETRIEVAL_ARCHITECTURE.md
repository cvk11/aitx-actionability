# Biomedical retrieval architecture

All evidence enters the system through typed retrieval functions that (1) call an official API, (2) register every returned record in the **evidence ledger** under a canonical key with URL, access timestamp, text scope and metadata, and (3) log the query (tool, arguments, result keys, error). LLM stages can cite only ledger keys; the renderer converts keys to links from the ledger, so a citation URL is never generated by a model.

## Sources

| Tool / function | Source (endpoint) | Ledger key | Text available for verification | Notes |
|---|---|---|---|---|
| `pubmed_search`, `pubmed_fetch_abstracts` | NCBI E-utilities esearch/esummary/efetch (PubMed) | `PMID:<n>` | metadata → abstract | Retraction flag from publication types / CommentsCorrections; abstracts loaded before verification |
| `pmid_exists` (verifier) | E-utilities esummary | – | – | Deterministic existence check of every cited PMID |
| `europepmc_search`, `europepmc_fulltext_excerpts`, `load_fulltext` | Europe PMC REST (search, `fullTextXML`) | `PMID:` / `PMCID:` | all open-access full-text paragraphs **and table rows** (header + caption kept), location-labelled; supplementary files listed (not parsed) | Preprints flagged. Full text is loaded automatically for every cited open-access article before verification; non-OA articles are marked "abstract only; tables and supplements not accessible" |
| `variant_literature_search` | Europe PMC full-text search + PubMed title/abstract search with all common notations of the patient's variant (HGVS c./p., short forms, rsIDs) | `PMID:`/`PMCID:` | – | Run automatically in the bootstrap; variant notations often appear only in full texts/tables (e.g. 0 PubMed hits vs ≥1 Europe PMC full-text hit for the official ITPR1 variant) |
| `clinvar_lookup` | E-utilities (ClinVar esearch + esummary) | `CLINVAR:VCV…` | structured record | Registered only if the title denotes the same cDNA change on the **same transcript version** (`exact_transcript_version`), or on another version of the same accession **and** the record's canonical SPDI equals the patient's GRCh38 allele from VariantValidator after identical minimal left-aligned normalisation (`genomic_equivalent_other_transcript_version`; e.g. CFTR F508del VCV000007105 is titled on NM_000492.3). Other-version records without proven equivalence → `version_mismatch_candidates`; other variants → `non_matching_hits`; neither is evidence |
| `search_trials`, `get_trial`, `trial_status` | ClinicalTrials.gov API v2 | `NCT<8 digits>` | status, ages, sex, conditions, interventions, countries, full eligibility text | Status classes kept distinct: actively recruiting / not yet recruiting / enrolling by invitation / expanded access available. The verifier re-fetches every cited trial live and **overwrites** status, ages, sex and eligibility text; a failed live check is recorded as `status_verification=failed` (unverified, blocks submission), a 404 as not found. `next_page_token` pagination |
| `fda_label_search` | openFDA drug label API (DailyMed set id) | `FDALABEL:<set_id>` | label sections (indications, contraindications, boxed warning, pediatric use, interactions, PGx …) | Citation URL = DailyMed page |
| `clinpgx_gene_annotations` | ClinPGx (formerly PharmGKB) API | `CLINPGX:PA…` | gene flags | Old `api.pharmgkb.org` host unreachable via proxy |
| `genereviews_find`, `genereviews_read` | Local snapshot of the official NCBI litarch GeneReviews archive (see below) | `GENEREVIEWS:NBK…#<section>` | full section text incl. tables, cited PMIDs, chapter revision date | Citation URL = canonical Bookshelf chapter + section anchor |
| `annotate_variant` | NCBI nuccore feature table (RefSeq), VariantValidator, Ensembl VEP REST | `REFSEQ:`, `COMPUTED:`, `VARIANT:VV:`, `VARIANT:VEP:` | structured / computed | Deterministic transcript model, consistency checks. VEP is accepted only for the exact requested transcript version (no fallback to another transcript) |
| `gene_profile` | ClinGen (validity + dosage lists), gnomAD GraphQL v4 constraint, UniProt REST | `CLINGEN:`, `GNOMAD:`, `UNIPROT:` | structured | UniProt features overlapping the variant residue |
| `ncbi_gene_summary` | E-utilities (Gene) | `URL:https://www.ncbi.nlm.nih.gov/gene/<id>` | gene summary | |
| `fetch_url` | Allow-listed authoritative domains only | `URL:<final url>` | page text | Redirects followed manually; every hop must be on the allow-list before it is requested. Pages behind bot challenges reported as inaccessible, never bypassed |

No general web search is used (the organizers warn about SEO/predatory sources). OMIM is not used (requires a licensed API key; HTTP 403).

## Deterministic bootstrap (before any LLM call)
For each variant: RefSeq transcript model → computed features; VariantValidator (nomenclature + predicted protein, compared with the supplied `variant_protein`); VEP (consequence, exon, colocated ClinVar IDs; computed exon cross-checked against VEP); ClinVar exact-match lookup (cDNA, then protein notation fallback). For each gene: ClinGen validity/dosage, gnomAD constraint, UniProt features at the residue, NCBI Gene summary, GeneReviews chapters, open trials by gene term. The dossier and the ledger keys are passed to the interpreter.

## Outcome categories (never conflated)
`EvidenceLedger.retrieval_status()` classifies every source per run as **with_results**, **empty** (the query ran; the source has no matching record) or **failed** (timeout/HTTP error; nothing can be concluded), and counts **truncated** searches (the source reported more hits than were reviewed; PubMed/Europe PMC/ClinicalTrials.gov support `page`/`page_token`). "Record found but does not support the claim" is captured by claim verification, not by retrieval status. Prompts (rule 10 in `prompts/common_rules.md`) require the model to distinguish "not found in X", "retrieval from X failed", and a confirmed negative stated by an authoritative source. Empty-section text in the report is generated deterministically from the query log and states either "Searched: … ; absence from these sources does not establish that none exists" or "Retrieval from … failed during this run, so no conclusion can be drawn", and mentions when only the first page of a larger result set was reviewed. Drug-repurposing items carry a scoped, dated statement ("No human treatment precedent … was identified in the literature searched in this run (…, accessed …); this does not establish that none exists") or, if literature retrieval failed or was not run, say so. Tested in `tests/test_milestone_checks.py::test_failed_retrieval_is_not_reported_as_absence`.

## GeneReviews provenance
GeneReviews chapter pages (`ncbi.nlm.nih.gov/books/NBK…`) serve a reCAPTCHA to automated clients, and Europe PMC book pages a Cloudflare challenge; neither is bypassed. NCBI distributes the full book through its literature archive: `scripts/build_genereviews_index.py` reads `https://ftp.ncbi.nlm.nih.gov/pub/litarch/file_list.csv`, streams `gene_NBK1116.tar.gz`, extracts only chapter `.nxml` files and downloads the gene→chapter maps from `https://ftp.ncbi.nlm.nih.gov/pub/GeneReviews/`. `data/genereviews/MANIFEST.json` records the archive URL, archive "last updated" date, SHA-256 of the streamed archive and build time. Snapshot used in development: archive last updated 2026-10-25 03:29:28, SHA-256 `af162f39cd026ab27cb0d31f5dfcb1f7dd0c7c5c261219bd61c2182f5ef49734`, 1017 NXML files, built 2026-11-01T22:42:20Z.

**Licensing:** GeneReviews chapters are © University of Washington; the copyright notice in the archive permits reproduction for non-commercial research purposes with credit, a link to the original, and no modification. The snapshot is therefore **not committed** to the repository (`.gitignore`) and is rebuilt reproducibly; reports quote only short facts and always link the original chapter.

## Network behaviour
`src/aitx/http.py`: per-host rate limits (NCBI 3 req/s, 9 with `NCBI_API_KEY`), explicit timeouts, tenacity retries (4 attempts, exponential jitter) on 429/5xx/transport errors, disk cache (7 days; trials 12 h) disabled in deployment mode, in-memory cache per process. API keys/emails are excluded from cache keys and from recorded URLs.
